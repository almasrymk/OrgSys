### Things discovered during testing that apply to every future feature

1. **Permission keys are one blanket key per entity, not per CRUD action, for some entities but not others.** Country only has `Countrys.All` (note the typo — "Countrys"). City/District/Currency/FiscalYear each have a full `*.All`/`*.View`/`*.Add`/`*.Edit`/`*.Delete` set. **Grep `Infrastructure/Seed/InitialData.cs`'s `InitialPermission` for the actual keys of each entity before wiring `*appHasPermission` or `menu.config.ts`** — don't assume a pattern, and don't port what an MVC Razor view happens to check (some, like Country's, reference the wrong entity's keys — a copy-paste artifact in the original app).
2. **The seeded `Owner` role (RoleId=1) has zero `RolePermission` rows.** `LoginCommandHandler` requires at least one resolved permission or it returns `NotFound` — so logging in as `Owner` fails via the API even with the correct password, despite `RoleId==1` being treated as "always allowed" everywhere else (MVC's `IsAllowed`, and this app's `PermissionService`/`JwtTokenService`). Use the seeded `Admin`/`P@ssw0rd` user for testing instead. This is pre-existing seed data, not something introduced here — worth a decision on whether `LoginCommandHandler` should special-case the owner role, but that's an Application-layer change outside this task's scope.
3. **Command DTO shapes vary per entity** — check before wiring a form: Country/City use plain `record` commands with only the fields that change (`CreateCountryCommand(string Name)`); District/Currency/FiscalYear use `Create*Command : *Dto` subclasses (the full DTO), so one request shape covers both create and update (`id` optional). Grep the actual `Commands/*.cs` file rather than assuming either pattern.
4. **Cross-field/absolute-positioned CSS bugs are easy to introduce and easy to miss without a real viewport test.** The first form (`country-form`) used `position-absolute` for its "Back" button; at 1000px+ width it looked fine, but the same pattern in `city-form` (one extra field, taller card-body) overlapped the Name input at narrower widths and silently ate the first click on that field during testing. Fixed everywhere by replacing `position-absolute` with a `d-flex justify-content-end` header row. Worth actually rendering each new form in a browser, not just reading the template.
5. **Audit fields (`CreateUserId`/`CreateDate`/`ModifyUserId`/`ModifyDate`) are not server-assigned.** OrgSys.App's MVC `MainController.FixData()` sets these from the authenticated session before every Create/Update — `CreateUserId` is a **required FK to `User`**, so omitting it isn't silently ignored, it's a 500 (`FK_Journal_User_CreateUserId` violation, caught live while testing Journal create). Any entity descending from `MovementDto` (Journal, and presumably Financial/Invoice/Transaction/Inventory when their turn comes) needs the Angular form to set these explicitly from `AuthService.currentUser()!.id` + `new Date()`, preserving the original `CreateUserId`/`CreateDate` on edits and only touching `ModifyUserId`/`ModifyDate`. Grep for `FixData` overrides in the corresponding MVC controller before building the next `MovementDto`-based screen.
6. **Child-collection FKs aren't always set by the server either.** Journal's `UpdateCommandHandler.SaveDetials` maps `JournalItemDto` straight to the `JournalItem` entity via AutoMapper without ever assigning `JournalId` in code (unlike FiscalYear's equivalent handler, which does set `FiscalYearId` on each period) — caught live as a second FK violation (`FK_JournalItem_Journal_JournalId`) after fixing #5. The client must set the child's FK explicitly on every line. **Don't assume a parent/child save handler fills in the FK — check `SaveDetials` in the specific `UpdateCommandHandler` for each entity that has one.**
7. **A new `MovementDto`-based record can't get its lines attached in one call.** `CreateJournalCommand`'s handler never calls `SaveDetials` — only `Update` does — so a brand-new Journal must be created header-only, then looked up by its unique `Code` (Create's `Result` carries no Id) and immediately updated with its lines. See `JournalService.createWithLines()`, which encapsulates this so `journal-form.component.ts` just calls one method. Check whether the same split exists before building Financial/Invoice/Transaction (their `Create` handlers may or may not have the same gap — verify per entity, don't assume).
8. **`Financial` is not created through the generic Create/Update at all.** For every FinancialType except Opening Balance, `POST /Financial/Transactions/Post` (`PostFinancialTransactionCommand` / `PostFinancialTransactionDto`) is the only way in — it creates the row **and posts it in the same call**, immediately linking a balancing Journal. There is no Draft state reachable in practice for these types, so Edit/Delete/Cancel/Redo are dead buttons for them — only **Reverse** ever applies (`financial-transaction-list.component.ts` only offers that one action). Don't build an Edit screen for these types; there's nothing for it to edit.
9. **Found and fixed a real backend bug, not an Angular gap: `Financial.PaymentTypeId` is a required FK with no way to set it.** `PostFinancialTransactionDto` has no `PaymentTypeId` field, and `PostTransactionCommandHandler.Handle` never set one when constructing the `Financial` entity — every transaction post failed with `FK_Financial_PaymentType_PaymentTypeId` regardless of client. Fixed by defaulting to `PaymentTypeId = 1` ("Cash", `Infrastructure/Seed/InitialData.cs`), matching the convention `PostFinancialOpeningBalanceCommandHandler` already uses. **This blocked the endpoint for every caller, not just Angular** — worth confirming MVC's own Financial/Save flow was actually exercised against a FK-enforcing DB before this fix, since it would have hit the identical error.
10. **`computed()` does not react to a Reactive Forms `FormControl.value` change** — `FormControl.value` is a plain mutable property, not a signal, so a `computed(() => control.value ...)` only evaluates once (on first read) and then caches that forever. Caught live: `referenceNeedsCounterAccount` was `computed()` over `form.controls.referenceType.value`, cached `true` from the form's initial state, and silently stayed `true` after switching the reference type to Customer — blocking every Receipt/Payment submit that should have skipped the manual Counter Account field. Fixed by making it a plain method instead (Angular's template change detection calls it every cycle, which is correctly reactive here). **Never wrap a FormControl read in `computed()`** — use a plain method, or bridge it properly with `toSignal(control.valueChanges)` if a true signal is needed.
11. **`FinancialTransfer.Post` creates two `Financial` legs the exact same way `PostTransactionCommandHandler` does — same missing `PaymentTypeId` bug (#9), independently present in a second handler.** Fixed with the identical one-line default before ever trying to test the Transfer feature live, since the pattern was already known. **When two handlers construct the same entity type by hand, check both for the same gap rather than assuming a fix in one covers the other.**
12. **Found and fixed a second, more systemic backend bug: `GlobalExceptionMiddleware` serializes error responses in PascalCase, breaking every camelCase-based client-side error read.** Every normal controller response goes through `AddControllers().AddJsonOptions()` in `Program.cs` (camelCase). But `GlobalExceptionMiddleware.WriteResponse` calls `JsonSerializer.Serialize(result)` directly with default options — PascalCase — for anything that escapes a MediatR handler's own try/catch, notably `FluentValidationFilter`'s pipeline-level `AppValidationException`. Caught live: an Opening Balance validation error ("An Opening Balance already exists...") came back as `{"StatusCode":400,"Errors":[{"MessageError":"...","Key":"..."}]}` instead of `{"statusCode":...}` — every `result.errors?.[0]?.messageError` read in this codebase would have silently gotten `undefined` and shown a generic "X failed." toast instead of the real reason, for **any** validation error anywhere in the app that fails via the FluentValidation pipeline rather than being caught inline by the handler. Fixed by passing `new JsonSerializerOptions(JsonSerializerDefaults.Web)` to that one `Serialize` call. **This affected every feature already built, not just Financial** — worth manually re-checking a validation-error toast on a couple of the earlier screens (Country/City/Journal) now that it's fixed, since none of that testing would have caught the wrong casing (only the fallback message was visibly wrong, not a hard failure).
13. **Duplicate `Preference` rows for the same `(Reference, TypeId, Key)` exist in this dev DB** — e.g. two `CashBoxAccount` rows under `Financial`/`OpeningBalance`, one with the real configured value and one stale `"0"` row, most likely left behind when Preferences was reworked (`884dbab1` in git log) without deleting the old rows. `PostFinancialOpeningBalanceCommandHandler` (and presumably anything else reading `Preference` the same way) does `preferences.FirstOrDefault(e => e.Key == "...")`, which is unordered and non-deterministic — it happened to pick the stale `"0"` row, making Accounts-Integration-mode Opening Balance posting fail with "Cash Box Account is not configured" even though it was. Deleted the three stale rows (`Preference` ids 2004-2006) as data cleanup to unblock testing. **Not a code fix** — worth a decision on whether `Preference` needs a uniqueness constraint on `(Reference, TypeId, Key, UserId)` and/or whether the Preferences save flow should upsert instead of insert, but that's an Application-layer/data-integrity question outside this task's scope. Worth checking for the same duplicate-row pattern under other `Reference` values (Invoice, Transaction, Journal, Inventory) before relying on their Preferences too.
14. **Found and fixed a third backend gap: `Dealer`'s list/search/get-by-id queries never loaded `Country`/`City`/`District`, so `DealerDto.CountryName`/`CityName`/`DistrictName` always came back `null`** even though `CountryId`/`CityId`/`DistrictId` themselves saved and read back correctly (`DealerGroup,Account` were the only navigations in `CreateInclude()`; `GetByIdQueryHandler` had no override — and thus no Include — at all). Caught live: a customer saved with a real City still showed a blank City column in the list. Fixed by adding `Country,City,District` to all three handlers' includes. **Grep `CreateInclude()` for the entity before trusting a DTO's `*Name` display field is actually populated** — the FK saving correctly doesn't mean the read side loads the navigation to resolve its name.
15. **My own gap, not a backend one: forgot `code`/`codeNumber` in the Invoice save payload entirely** — `getMaxCodeNumber()` was fetched and displayed in the header, but never actually included in `submit()`'s payload, so every created Invoice saved with `code: null`. Caught live by checking the row after create, not by any error (this doesn't violate a FK or fail validation — it just silently saves wrong). **A quiet no-error data gap is easy to miss without actually reading back what was saved** — worth spot-checking one saved record's raw fields per new entity, not just confirming the save call returned success.
16. **Child-collection FKs**: confirmed the same "client must set the FK explicitly" rule from Journal (#6) applies to `InvoiceProduct.InvoiceId` on Update too — set it defensively from the start this time (`invoiceId: id` on every line in the Update payload) and it worked first try, no repeat debug cycle. Worth checking as a standing rule for every future `MovementDto`-with-child-collection entity (Transaction/Inventory when their turn comes): **assume the child FK is not auto-populated on Update unless the specific handler's `SaveDetials` proves otherwise.**
17. **A header-level `Total`/`Net` aggregate is a client-supplied field, not server-computed, for `Transaction` too (same class of gap as #15, but caught before shipping this time).** `Areas/Transactions/Views/Transaction/Save.cshtml`'s JS computes `AllTotal` client-side and posts it as `Total` — nothing in `CreateTransactionCommandHandler`/`UpdateTransactionCommandHandler` sums `TransactionProducts` into `Transaction.Total`. Caught live: first save of an Addition transaction round-tripped every line correctly (`quantity`/`cost`/`total` all persisted right) but the list showed `Total: 0.00`, because `SaveTransactionRequest.total` was never sent. Fixed by adding `total: this.linesTotal()` to the payload and the model, rebuilt, re-tested — a Transfer (60.00 = 3×20) then displayed correctly. **Any future `MovementDto`-based entity with a header aggregate field (`Total`/`Net`/etc.) should be assumed client-computed-and-sent unless a handler proves otherwise — grep the MVC Razor view's save JS for the field name, not just the CQRS handler, since the aggregation logic often lives only in the old client-side JS.**
18. **Found via Reports testing, not Invoice testing: the same "header aggregate is client-computed" gap from #15/#17 also applies to `Invoice.NetByDefaultCurrency`, and it shipped silently in the already-built Invoice feature.** `CreateInvoiceCommandHandler`/`UpdateInvoiceCommandHandler` never derive `NetByDefaultCurrency` from `Net * Rate` — it's a plain client-supplied field, same as `Financial.AmountByDefaultCurrency`. The Angular Invoice form (built in Phase 6, before Reports surfaced this) never set it, so every Invoice created through Angular silently saved `netByDefaultCurrency: 0` — invisible in the Invoice screens themselves (they only ever read/display `net`), but it broke every downstream report keyed on it (Dealer Balance/Statement, Sales Balance all read `NetByDefaultCurrency`, per finding #19 below). Caught live: a test Invoice with `net: 150` showed `balance: 0` on the Clients Balance report until this was fixed. Fixed by adding `netByDefaultCurrency` to `invoice.model.ts`'s `Invoice`/`SaveInvoiceRequest` and computing it as `grandTotal() * rate` in `invoice-form.component.ts`'s `submit()`. **The general lesson from #15/#17/#18, now confirmed three times across three different entities: any `*ByDefaultCurrency`/normalized-amount field is client-computed everywhere in this codebase, never server-derived — grep for the field's usages (not just its presence) in downstream reports/queries before assuming a screen that doesn't display a field can skip setting it.**
19. **Reports module**: built net-new (`Application/Commands/Org/Reports/*`, `API/Controllers/Org/Reports/*`, Angular `features/reports/*`) since MVC's `Areas/Reports` had no CQRS/Application layer at all — see the Reports row in the table above for full detail. Legacy bugs found while researching the old (git-history-only) `Service`/SQL layer and deliberately **not** ported: (a) Stock Movement's legacy SQL had its entire filter clause dead/commented out (ported using its working twin, Product Movement's filter, instead); (b) Suppliers/Clients Statement's legacy SQL had `1 = 2` hardcoded into both opening-balance sub-selects, permanently zeroing them out — replaced with a real running total of everything before `FromDate`; (c) Safe Balance was never wired up end-to-end in MVC at all (the controller's real call was commented out) — rebuilt fresh, simplified to one row per CashBox rather than the unfinished legacy per-dimension breakdown. **When porting a legacy feature from git history rather than live code, verify each piece actually executes correctly in the original before treating its logic as the source of truth — dead/commented code sitting next to working code is easy to miss without reading the whole call chain.**
20. **`BankBranch.DistrictId` is a required non-nullable FK, unlike Dealer's optional `DistrictId`.** Both entities reuse the same Country→City→District cascade pattern, so it was reasonable to assume District is optional everywhere it appears (Dealer's `DistrictId` is `long?`) — but `BankBranch.DistrictId` on the Domain entity is a plain `long`. Caught live: the first Bank Branch save with District left unselected (`districtId: 0`) failed with a 500 (`FK_BankBranch_District_DistrictId` violation, no District row with `Id=0`). Fixed by making District a required field in the form (`Validators.required, Validators.min(1)`), matching the entity. **Don't assume a repeated cascade pattern has identical nullability across every entity that uses it — check the specific entity's FK declaration (nullable `long?` vs plain `long`) even when the picker UI looks identical to one already built.**
21. **Found and fixed a fourth real backend bug, pre-dating Angular entirely: `ProductController`'s `GetMax` action used the wrong query type.** `API/Controllers/Org/Setting/ProductController.cs` was wired as `BaseController<..., GetMaxAccountQuery, ProductDto>` — `GetMaxAccountQuery`'s handler is hard-bound to `IRepository<Account>`, so `/Product/GetMax` silently computed the max `CodeNumber` from the **Account** table, not Product. This is a copy-paste artifact (every other entity has its own `GetMax*Query`) that predates this migration — MVC's own Product Save flow calls the identical `GetMax?TypeId=` endpoint for new-product code generation, so **this bug already existed in production MVC**, not something introduced by the API/Angular work. Fixed by adding `Application/Commands/Org/Setting/Product/Queries/GetMaxQueryHandler.cs` (`GetMaxProductQuery`, mirrors Account's own exactly) and rewiring the controller. Verified live: a new product now gets `640105` (real max `640104` + 1) instead of whatever the Account table's max happened to be. **A `GetMax*Query` reused across entities via a shared/generic-looking name is worth double-checking — grep the query's own handler for which `IRepository<T>` it's actually bound to, don't trust the controller's generic parameter list to be self-consistent.**

## 0. Architecture as found

- **OrgSys.App (MVC)** is a BFF: most controllers extend `MainController<TDto,TCreate,TUpdate>` and call the **API** project over plain `HttpClient` (`{ApiUrl}/{Entity}/{Action}`, no `api/` prefix except `/api/Auth/*`). A few legacy controllers (`Order`, all of `Areas/Reports`) bypass CQRS/API entirely and call old `Service`/`Entity` classes in-process against the DB directly — **these are not on the CQRS/API stack at all**.
- **Auth today: cookie-based, MVC-only.** `Startup.cs` configures cookie auth; login claims include a `ClaimTypes.Webpage` claim = CSV of permission keys resolved once at login. `User.IsAllowed("Key1,Key2")` (an extension method) is checked ad hoc in a handful of controllers (`Financial.Post`, `Financial.Reverse`) and pervasively in Razor views/the menu partial — **not** via `[Authorize(Policy=...)]`.
- **The API project has zero authentication** — no scheme configured, no `[Authorize]` anywhere, `Login` returns a `UserDto`+permissions with **no token**. It trusts whatever calls it (currently only the MVC app, same machine). **This is the critical gap for Angular**: a browser SPA cannot reuse this trust model as-is.
- Response envelope: API actions return `Result`/`Result<T>`/`ResultCollection<T>`/`ResultPagination<T>` directly with **HTTP 200 even on business failure** — success/failure is inside the JSON body (`StatusCode`/`Errors`). MVC's `MainController.Save()` already unwraps this; any Angular HTTP layer must do the same.
- Generic CRUD screens are parameterized by a `TypeId`/`ParentId` "type dimension" (`Financial?TypeId=2`, `Invoice?TypeId=1`, `Transaction?TypeId=3`, `FinancialAccount?TypeId=1|2`, `Dealer?TypeId=1|2`) rather than one controller per subtype — same idea the task brief describes for FinancialType, but it's used across Invoice/Transaction/Dealer/FinancialAccount too.

## 5. FinancialType-driven behavior (the pattern to preserve)

Single screen `Areas/Financials/Financial/Save.cshtml` + `FinancialController`, driven by `FinancialTypeId` (enum `FinancialTransactionType`: 1=OpeningBalance, 2=Receipt, 3=Payment, 4=TransferIn, 5=Deposit, 6=Withdrawal, 7=Fee, 8=Interest, 9=Cheque, 10=Adjustment, 11=TransferOut):

- **Title/icon**: resolved from `FinancialType` lookup row (`Name`, `Icon`) — no per-type hardcoding needed in Angular beyond a lookup call.
- **Direction lock**: `FinancialType.InOut` (1=In-only, -1=Out-only, 0=user choice) — only Transfer/Cheque/Adjustment let the user pick Direction.
- **Fiscal Year field**: only for OpeningBalance (TypeId=1); separate Draft→Post→Reverse workflow via `PostFinancialOpeningBalanceCommandHandler`, distinct permission checks (`Financial.Post`, `Financial.Reverse`).
- **Reference picker**: only for Receipt/Payment; source table depends on `FinancialReferenceType` (Customer/Supplier→Dealer, Expense/Income→Account, Invoice/Payment/Transfer→their own tables); Counter GL Account becomes read-only, auto-derived from the resolved reference.
- **Validation**: generic path requires `FinancialAccountId`, `Amount>0`, `CounterAccountId`; server (`PostTransactionCommandHandler`) re-validates per `ReferenceType` and re-derives the counter account — **this business logic stays in the API/Application layer**, Angular only needs to mirror it for UX (disable fields, inline hints), never as the source of truth.

Recommended Angular shape: one `financial-form` component/page in `features/financial/transactions/`, parameterized by `financialTypeId` (route param, same as MVC's `TypeId` query param), pulling type metadata (`InOut`, reference-type list, icon/title) from `/FinancialType/GetById` rather than hardcoding per-type branches. Same "one form, type param drives everything" pattern applies to `Invoice` (InvoiceType) and `Transaction` (TransactionType) — build the pattern once, reuse the approach for both.

## 6. Auth, permissions, menu, localization — mechanics to reproduce

- **Permissions**: string `Key` rows on `Permission`/`RolePermission`, flattened into the login response and (in MVC) a claim. Angular equivalent: `AuthService` stores the permission-key list from login response; a `PermissionService.can(key: string)` + a `*appHasPermission` structural directive replace `User.IsAllowed(...)`; a route-level `canActivate` guard replaces menu-hiding-as-security (note: MVC doesn't actually enforce this server-side on most Setting screens either — Angular should be *at least* as strict, but real enforcement must still happen API-side eventually).
- **Menu**: no DB table — extract the hardcoded groups/permission-key gating from `_MainMenu.cshtml` into an Angular menu config (`core/config/menu.config.ts`), each item carrying `route`, `permissionKeys`, `labelKey` (localization key), `icon`.
- **Preferences**: generic key/value scoped by `Reference` (module name) + `TypeId`, **not per-user** — model as a typed config object per feature (e.g. `FinancialPreferences`, `InvoicePreferences`) fetched once via `/Preference/GetList?Reference=X`, not a generic dictionary sprinkled through components.
- **Favorites**: doesn't exist server-side — do not build Angular UI for it until/unless the user asks for it as new scope.
- **Localization**: `.resx`-based (`Title.Designer`, `Message.Designer`, en + ar), culture switched via a cookie. Angular equivalent: `@angular/localize` or `ngx-translate` with `en`/`ar` JSON extracted from the resx files, `core/services/localization.service.ts` for runtime switch + RTL toggling (mirror `_Layout.cshtml`'s `dir` logic).

## 8. Migration order (revised for this app, incremental)

1. **Angular foundation** (this task, Phase 1) — core/shared/layout scaffolding, auth (pending the decision in the note below), interceptor for the `Result<T>` envelope, permission service, localization, menu config.
2. **Reference feature** — `administration/countries` (simplest: no cascading dependents, full CRUD already on the API). Establishes the CRUD pattern: list + form + service + model.
3. Roll the same pattern to City → District (adds cascading dropdown pattern), Currency, FiscalYear.
4. Accounting: Chart of Accounts (tree component), Journal Entries.
5. Financial: FinancialAccount, then the FinancialType-parameterized Financial form (highest complexity so far, do after the pattern is proven on Invoice or Transaction if those turn out simpler).
6. Customers/Suppliers (Dealer/DealerGroup), Invoices, Transactions/Inventory.
7. Reports — only after backend CQRS/API work closes the gap in §3; treat as its own mini-project.
8. Orders — pending stakeholder confirmation it's still in scope.

## 9. High-risk / high-complexity items

- **API authentication is missing entirely.** Nothing else can be safely called from a browser SPA until this is decided (see question below).
- **Financial/Invoice/Transaction "type-driven single form" screens** — most business logic (validation, counter-account derivation) lives server-side in Application handlers; Angular must not reimplement it, only mirror it for UX, so these forms need careful API contract review, not just UI porting.
- **Reports module** — needs net-new backend (CQRS+API) before any Angular work; largest single scope item in the whole migration.
- **Order module** — unclear if still in active use; low-confidence effort estimate until confirmed.
- **Result envelope with always-200 HTTP status** — every Angular API call needs the same unwrap-and-check-StatusCode logic MVC's `MainController.Save()` uses; easy to get subtly wrong per-feature if not centralized in one interceptor/service from day one.
- **Preferences naming** — "Preferences" in this app is tenant/module-wide config, not per-user; don't build a per-user settings UX by mistake.
